# The NPU load

The plan's phase 6 ([docs/PLAN.md](PLAN.md) §13/1) lists the NPU among
the loads to try, under its one rule: a load joins Full load only if
adding it measurably increases the watts. This note is the sketch, so
the experiment can start without re-deriving it. Nothing here is
measured yet.

## Why the NPU

No stress test stresses the NPU. On the reference phone the Hexagon
unit sits on the SoC like the CPU and the GPU, draws from the same
battery, and is invisible to every benchmark the phone's own "100 %"
number covers. If a sustained inference load draws measurable power,
it is the one load this app could carry that nothing else measures.

## What an app can reach

The phone gives no sysfs for the NPU: no frequency, no utilisation, no
temperature beyond the zones the thermal reader already groups. What
an app can do is run inference. The routes, most portable first:

1. **LiteRT (TensorFlow Lite) with the NNAPI delegate.** The vendor
   driver dispatches to the Hexagon itself: no vendor libraries, no
   permission, no network, on every phone whose driver answers. NNAPI
   the API is deprecated; the delegate still works, and the load sits
   behind one interface to swap later.
2. **Vendor delegates (Qualcomm's QNN/HTP).** The fastest route to the
   unit, but their libraries are not on every phone and their SDK is
   not redistributable. Not a route for an app for every phone; worth
   a per-device probe at most.

## The shape that fits this app

- A small committed model: stacks of large INT8 matmuls, weights
  chosen to fill the unit, a few hundred kilobytes. Generated by a
  `tools/gen_npu_model.py` (TensorFlow on the development machine) and
  committed beside its golden outputs.
- An `NpuEngine` that runs inference back to back on its own thread,
  in bounded batches like the CPU workers. Each inference's outputs
  fold into a digest compared against the first — the same discipline
  the CPU kernels and GPU burners follow, so wrong computation is
  counted, not assumed away.
- The workload text gains `npu` as a part, the way `scene+gpu_fp32`
  joined: `0-7:fp32_l2+npu` parses, `describe` round-trips, and a lab
  session can sweep it beside the other loads.
- The sampler needs nothing new: the power shows up in the battery,
  the heat in the thermal zones it already reads.

## Measure first

Before any of it is built: a harness in the device screen's manual
loads that runs the model for a minute, and a `tools/lab.mjs` session
against the plain idle. If the delta sits in the noise of the battery
gauge, the load does not join — that is the phase's rule, and the
cheapest way to know is the measurement, not the code.

## Risks

- **Deprecation.** NNAPI's removal would take the portable route with
  it; the LiteRT interface is the layer to replace, not the engine.
- **Driver variance.** Some vendor drivers answer NNAPI requests
  slowly or refuse accelerators; the engine must fail into "no NPU
  load" the way the GPU engine fails without Vulkan 1.1, and the
  capability check must run before the mode is offered.
- **Determinism.** An NPU's rounding is its own; the digest is
  compared against this run's first inference, not a committed number,
  which is what the CPU kernels already do.
